專案介紹

核心設計理念與整體定位。

本專案是一個常駐型 Twitch 聊天機器人，透過 twitchio 監聽 IRC 聊天訊息、 透過 twitchAPI 的 EventSub WebSocket 接收忠誠點數兌換事件， 並以 Helix API 執行 VIP 授予與移除。

架構上最大的特色是「Bot 主程式 + 本地微服務」的拆分： Google Sheets、OpenAI、MongoDB Atlas、YouTube 四種外部資源都不直接在 Bot 內呼叫， 而是各自由一個本地 HTTP 服務代理，Bot 端僅保留輕量的 HTTP Client（svc_client 套件）。 這讓外部依賴的憑證與 SDK 版本可以獨立於 Bot 演進。

第二個特色是「Google Sheets 作為 CMS」： 指令觸發詞、回覆內容、轉職表、食物清單、諧音梗等營運內容全部放在試算表， 指令派發器（command_dispatcher）依表格設定動態載入對應的 Python 函數， 新增指令不需要動到程式碼。

    營運架構決策

    「機器人只在開台期間運作」該由誰保證？2026-08-09 的評估、結論與已上線的觀測。

    目前 Bot 採本機手動啟動：不容器化、不上雲、不設開機自啟。 這不是還沒做，而是刻意的——用「進程不存在」來保證「關台期間不會有人洗經驗值」。 本節記錄的是：Twitch 到底抓不抓得到開台／關台，以及若抓得到，架構該不該改。

    一、事實查核：開台與關台都抓得到

    已核對 Twitch EventSub 官方文件與本機安裝的 twitchAPI 4.5.0。兩個事件都存在， 而且完全不需要新增任何 scope。 專案已有一個 EventSubWebsocket（訂閱忠誠點數），加兩行 listen 就能同時收到。

    項目stream.onlinestream.offline
    需要的 scope不需要不需要
    conditionbroadcaster_user_idbroadcaster_user_id
    傳輸方式Webhook / WebSocketWebhook / WebSocket
    事件內容含 started_at僅頻道識別資訊
    twitchAPI 方法listen_stream_online()listen_stream_offline()

    但有四個必須先知道的限制：

    • WebSocket 只吃 user access token——官方明講用 app token 訂閱會失敗。本專案本來就是 user token，無影響。
    • 斷線等於訂閱全滅，事件不補發。WS 一斷，該 session 所有訂閱自動停用，重連後必須重新訂閱，斷線期間的事件永久遺失、沒有 replay。半夜斷線沒人發現，隔天開台的 online 事件可能根本收不到。
    • stream.offline 會抖。推流短暫中斷有機會產生一對 offline → online。把關台直接當成停止服務的訊號，一次網路抖動就會誤判下台。
    • 事件有延遲，不是即時的。

    後兩點屬於實務上的普遍觀察，官方文件並未承諾具體的延遲上限或抖動行為。 因此若真要依賴這兩個事件，必須搭配 Helix Get Streams 定期對帳， 用「當下的真實狀態」而非「收到的事件」作為單一事實來源。

    二、需求其實有兩層

    「只在開台期間運作」可以拆成 (a) 進程要不要一直活著 與 (b) 機器人要不要一直回應。現況把兩者綁在一起，但它們可以脫鉤—— 於是實際上有三個選項，其中一個直接出局。

    方案進程回應評價
    A 手動啟動只在開台期間只在開台期間現況
    B 常駐 + 開關台閘門24 小時只在開台期間需要新邏輯
    C 常駐、永遠回應24 小時24 小時與需求衝突，排除

    三、A 與 B 的優劣

    A · 手動啟動現況
    優勢
    • 需求由架構天然保證，零信任成本。進程不在就不可能有人洗錢，不依賴任何判斷邏輯的正確性。
    • 「每場開台固定內容」是免費的。!吃、!梗、招呼名單的快取隨進程生死，語意剛好就是「本場」。
    • 除錯最直接，終端機就在眼前。
    • 零基礎設施、零常態成本。
    • 改完程式下次開台即生效，沒有部署流程。
    劣勢（已依實際使用習慣重新評估）
    • 要記得手動開 → 不成立：開台前一定會開，忘了觀眾也會提醒。
    • 中途掛掉沒有人救 → 影響可接受：家用電腦每天重開機，且「當次開台沒機器人就算了」。
    • 綁在一台機器上 → 原判斷是誤判：四個微服務都已各自容器化（各有 Dockerfile / compose.yaml），網址也讀設定檔而非寫死。真正缺的只是「這個 repo 裡沒有那四個服務的清單」，補一份文件即可。
    • 長期任務無處可掛（VIP 到期當天移除、每日統計）。
    • 開台前幾分鐘有空窗，觀眾比機器人早到。
    B · 常駐 + 開關台閘門
    優勢
    • 不會忘記開，而且開台當下就已在線，沒有空窗。
    • 可以自動重啟，掛掉自己爬起來。
    • 長期排程有地方掛，VIP 每日到期掃描變成自然的事。
    • 可以在關台後做事（結算當日排行、產出數據）。
    • 會強迫把「哪四個服務、怎麼一起起來」寫成一份設定。
    劣勢
    • 需求從架構保證退化成邏輯保證。閘門有 bug 就會「沒開台卻在發經驗值」，而這件事頻道主看不到——正是最在意的失效模式。
    • 狀態偵測有一整圈邊界情況：斷線不補發、offline 抖動、事件延遲，都要靠對帳兜底。
    • 「每場固定內容」得自己實作，由 stream.online 觸發清快取。
    • 持續佔用電力、記憶體、Atlas 連線。
    • 改版要重新部署，新增基礎設施維護面。

    結論：維持 A 手動啟動

    A 的五項劣勢裡，前兩項被使用習慣消化掉了，第 3 點經澄清後是誤判（微服務早就容器化了）， 第 4、5 項是能接受的取捨。這條路線目前沒有未解的嚴重風險。

    反過來，B 的最大劣勢正好打在頻道主最在意的地方。 用「進程不存在」保證需求是零成本、零 bug 的；換成程式邏輯， 就換成了需要測試與維運的保證。在還沒有非常駐不可的需求之前，不值得做這個交換。

    什麼時候該重新評估
    • 出現任何離線也生效的權益（例如 VIP 要在到期當天就移除）
    • 開台頻率變高，或有其他人代管，忘記開的成本上升
    • 想累積跨場次的數據
    若真要切換，最小順序
    • ✅ 已完成：訂閱 online / offline，只寫 log 不改行為，跑幾週觀察可靠度與抖動
    • 加 Helix Get Streams 定期對帳，確立單一事實來源
    • 才把閘門接到 handle_message 最前面
    • 最後才容器化與開機自啟

    還有一個折衷方案：拆成兩個進程—— 一個常駐的小型 worker 只負責 VIP 到期掃描與每日統計，聊天 Bot 仍然手動啟動。 這樣既拿到常駐的好處，又完整保留「進程不存在＝絕對不會回應」的強保證， 閘門邏輯根本不需要存在。以目前的專案規模，這很可能是投報率最高的路。

    四、觀察期：已上線的開台／關台觀測

    已在 main.py 的 event_ready 訂閱兩個事件， 只寫 log、不改變任何行為。 兩個 handler 都各自包 try/except——觀測用的程式碼絕不能反過來影響 Bot。

    • handler：MyBot.on_stream_online() / on_stream_offline()
    • log 標記：[STREAM-EVENT]（刻意用純 ASCII，方便 grep）
    • 查看方式：grep STREAM-EVENT logs/tm_twitch_bot.log

    觀察期要回答的三個問題：

    問題怎麼判斷
    事件會不會漏？每場開台是否都有對應的一行；有沒有只有關台沒有開台的情況
    offline 會不會抖？同一場直播中途是否出現「關台 → 開台」成對事件；stream_id 是否改變
    延遲多久？比對 log 時間戳、事件裡的 started_at、以及自己實際按下開台的時間

    三題答案都令人滿意，才有資格進行下一步（Helix 對帳）。 若發現會漏、會抖，就代表 B 架構的成本比預估更高，維持 A 的決定更加穩固。

    五、微服務的獨立性：原則正確，落差已補上

    四個本機微服務都是自行開發並已容器化，各自的專案資料夾有自己的 Dockerfile 與 compose.yaml；Bot 端的網址也讀 config_common.yaml 的 svc_url，沒有寫死。 「微服務應獨立部署、掛掉不影響主體」這個原則本身完全正確—— 但實際查證後，四個裡曾有一個並不成立（已於 2026-08-09 修正）。

    服務Port掛掉時的實際影響誰擋住的
    Google Sheets9091Bot 完全起不來 → 降級上線，5 分鐘自動重試main.load_sheet_config
    OpenAI9092!gpt 回制式錯誤訊息，其餘正常command_dispatcher
    MongoDB9093該次訊息的獎勵存不了並記 log，其餘正常message_controller
    YouTube9094!找歌 回制式錯誤訊息，其餘正常command_dispatcher

    原因是 main() 的 bootstrap 直接 await 兩個 Sheets 呼叫且沒有 try， 例外會一路拋穿。而 9091 偏偏是四個裡最容易忘記開的一個—— 它只在啟動那一瞬間用到，開台途中完全不會再碰。

    已修正：改為降級啟動。載入失敗只記錄並在聊天室公告， Bot 照常上線；之後每 5 分鐘重試一次，服務晚一點開起來就會自動恢復並再公告一次。 少了指令集仍然有打字給經驗值、升級、!排行、終極密碼、一桶金、VIP 掃描可用—— 一半以上的功能還在線，比「整場開台沒有機器人」好得多。

    四個微服務現在都符合「掛掉不影響主體」的原則了。

    六、防線放在哪一層：一個被漏掉的指令證明了原本的位置是錯的

    第七輪查到一個長期存在但沒人發現的缺陷：終極密碼的開場訊息，觀眾其實看不到內容。 guess_number_game.start() 用三引號多行字串組訊息，而 twitchio 的 Messageable.send 是把內容原樣內插進 PRIVMSG #頻道 :{content} ， 它的 check_content 只驗長度 500、完全不管換行。 實測那則訊息在線路上會被切成三行：

    IRC 線路上的第幾行內容結果
    [0]PRIVMSG #tigermeowtw :@老虎喵喵喵觀眾只看到一個空的 @ 提及
    [1]🎮 終極密碼開始！隨機產生數字於：0 ~ 1000，變成無效 IRC 指令，靜默消失
    [2]輸入『 !猜 <數字> 』每次猜測費 5，沒猜中灌注 2 進彩金池同上

    遊戲照常開始，但沒人知道規則與範圍。真正的問題不在這一支遊戲，而在 防線放錯了層：換行整平原本只做在 AI 回覆那條路 （ai_actions/tm_ai_agent.py），可是「不能有換行」是每一則出站訊息都適用的 Twitch 協定限制，和早就放在 chat_sender 的長度截斷完全同類。

    已修正：查過全專案的出站呼叫點，繞過 chat_sender 直接碰 channel.send 的地方是 0 處，所以把換行整平搬到那一層， 一次蓋住所有指令——包括 ai_actions/duel.py 回傳的 battle_log， 那是模型生成的自由文字直接進聊天室，而它的 system prompt 只禁了 Markdown、沒禁換行。 搬下去之後 AI 那側的處理整個刪掉，淨少 50 行程式碼。

    教訓不是「這支遊戲寫錯了」，而是「同一類限制散在各處做，漏掉的那次沒有任何東西會攔住」。 現在 chat_sender 是唯一的出站瓶頸，換行、長度、速率三道保護都在那裡。
